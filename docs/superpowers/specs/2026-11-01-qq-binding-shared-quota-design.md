# QQ 绑定与 QQ 独立额度设计

> 日期：2026-11-01
> 状态：待评审

## 1. 意图

梅林已经有 QQ 通道（群里 @ 才回话），但 QQ 用户和博客账号之间没有任何关系：不知道谁是谁，也没法计额度。这一版把两者接起来：

- 读者在博客注册后，可以在个人资料页拿到一串**绑定码**，在 QQ 私聊里发给梅林完成绑定；
- 绑定后，QQ 私聊和群里 @ 都能正常聊天；
- 绑定账号就是额度账号：默认 QQ 走一套独立的 QQ 额度，站长可以在 WordPress 后台切换成"QQ 与网页共享同一份额度"；
- 无论哪种模式，QQ 都有一个全站总额度兜底，避免有人刷爆。

## 2. 目标与非目标

**目标**

1. WordPress 个人资料页（`wp-admin/profile.php`）出现一张"Live2D 小助手 · QQ 绑定"卡片：当前状态、绑定码、刷新、解绑。
2. 未绑定的 QQ 私聊梅林 → 固定引导文案，教用户去哪里拿码、发什么命令。
3. 已绑定 → QQ 私聊可用；群聊里 @ 梅林也可用（仍受群白名单限制）。
4. 额度双模式 + 一个 WordPress 后台开关。
5. QQ 独立模式下一套并行额度：QQ 每人每日、QQ 会员每日、QQ 全站每日，外加"QQ 不限量"总开关；**这些参数全部在 WordPress 后台设置，改完立即生效**。
6. QQ 全站总额在两种模式下都生效。
7. 每次收到需要回复的 QQ 消息都回一次（提示、错误、正常回答都算），不做时间窗静音。
8. 命令系统是一个注册表（§4.5）：以后加命令只加一项，`/帮助` 自动列出，消息处理流程不用改。

**非目标**

- 不给 QQ 侧做账号体系：不设 QQ 密码、不做 QQ 账号注册。
- 不做网页解绑以外的方式解绑（QQ 里发"解绑"一律拒绝，见 §4.4）。
- 一个 WordPress 账号只绑一个 QQ，一个 QQ 只绑一个账号；不支持多对多。
- QQ 侧不消费"额外额度"（extra credits），那是网页账号的概念。
- 不做 QQ 群管理命令、不做消息撤回、不做多机器人实例。
- 不做任何**主动推送**：没有定时提醒、没有"你还没绑定"的催促，只在收到消息时回复。
- 斜杠/反斜杠开头的消息一律按命令处理，**永不交给梅林**，也不写入对话历史。
- 不改现有的群白名单、@ 触发、前缀触发逻辑。

## 3. 现状（实现本设计时要读的代码）

- `backend/app/channels/qq/adapter.py`：只解析 `message_type=group`；`handle_event()` 里先查群白名单、去重、取触发文本，再调 `_reply()`。
- `backend/app/api/qq.py`：OneBot 反向 HTTP 入口，验 token/签名后丢后台任务。
- `backend/app/credits.py`：`user_profile` 表里已有 `qq_uin`，但**从未写入**；`tier_of()` 负责会员到期降级。
- `backend/app/quota.py`：`reserve()` 三段式（每日 → 额外额度 → 全站硬上限），单事务。
- `wordpress-plugin/wp-live2d-ai/wp-live2d-ai.php`：`/wp-json/l2d-ai/v1/token` 给浏览器发用户 JWT；后台设置页负责 `PUT /api/admin/settings`。
- `wordpress-plugin/wp-live2d-ai/includes/class-l2d-ai-users.php`：后台"用户与额度"页，`qq_uin` 列目前永远显示"—"。

## 4. 绑定流程

### 4.1 个人资料页卡片

位置：只在 `wp-admin/profile.php`（自己的资料页）用 `show_user_profile` 钩子插入。不注册新路由——用户已经在用这个页面，多一个页面只会让人找不到。

管理员看别人的绑定状态，去后台"用户与额度"页看 `qq_uin` 列即可；`user-edit.php` 不加卡片（避免"管理员看到别人的绑定码并把自己的 QQ 绑上去"这类越权路径）。

卡片内容（用 WP 后台自带的 `.card` 样式，加少量内联 CSS，不引入前端框架）：

```
┌ Live2D 小助手 · QQ 绑定 ────────────────────────┐
│ 状态：未绑定                                      │
│ 绑定码：  1234-5678      [复制] [刷新绑定码]      │
│ 在 QQ 里私聊梅林，发送：/绑定 1234-5678            │
│ （复制按钮失败时请手动选中复制）                   │
│ [解绑]（仅在已绑定时出现，点击需确认）             │
└──────────────────────────────────────────────┘
```

- 已绑定时：显示"状态：已绑定 QQ 123456789"，绑定码区域换成一句"如需换绑，请先解绑再刷新绑定码"。
- 后端不可达时：显示"暂时无法同步绑定状态，请稍后刷新页面"，不显示按钮。
- 所有输入输出走 `esc_html()` / `esc_attr()`，按钮提交走 `admin-post.php` + nonce + `manage_options` 以外的**本人能力校验**（`current_user_can('edit_user', $user_id)`），管理员替别人看时不显示可操作按钮。

### 4.2 绑定码

- 8 位纯数字，显示为 `XXXX-XXXX`；生成用 `wp_rand()`，避免 `rand()` 的可预测性。
- **长期有效，直到手动刷新**（用户明确要求可手动刷新，不要限时）。
- 明文只存在 WordPress 的 user meta（`l2d_ai_qq_bind_code`）；后端只存 **SHA-256 哈希**（`user_profile.bind_code_hash`）。
- 刷新、解绑都会生成新码，旧码立即在两端失效。
- 用户打开资料页时，如果本地没有码就生成；如果本地码与"最后同步给后端的哈希"不一致（meta `l2d_ai_qq_bind_code_synced`），就用用户身份的 JWT 再推一次。

### 4.3 绑定命令

QQ 私聊里发送，大小写与空格不敏感：

```
/绑定 1234-5678
\绑定 12345678
/bind 1234 5678
```

**命令前缀是硬规则**：所有命令必须以 `/`、`\` 起手（全角 `／`、`＼` 等价）。系统代码先用正则把命令**截出来**：

```
^\s*[\/\\／＼]\s*(?P<cmd>[A-Za-z一-龥]+)\s*(?P<args>.*)$
```

- 命中正则 → 交给命令分发器，**消息正文（含前缀）永不进入 agent、不写入对话历史**；
- 以 `/` 或 `\` 开头但命令词不认识 → 回固定提示"这条咒文我没见过呢…… 我目前只会『/绑定』这一条。"，同样不交给梅林；
- 没有前缀的消息 → 照常走 agent（私聊/群聊规则见 §5）。

命令词大小写不敏感（`/BIND` 等同 `/bind`）；`/绑定` 的参数会先去掉空格、连字符、全角空格，剩余部分必须是 8 位数字，否则按"格式不对"回一句提示。

在群里发 `/绑定 ...`（带 @ 触发）不执行绑定，只回"私聊我一下，我把流程告诉你"——绑定码不能在群里经手。

判定顺序（全部在同一个 SQLite 事务里）：

1. 码哈希查不到 → 回"这串咒文对不上呢……回博客的个人资料页看看最新的绑定码吧。"
2. 这个 QQ 已经绑定了某个账号 → 回"我早就记住你啦。要是想换绑，得先回博客那边解绑一下哦。"
3. 目标账号已经绑定了别的 QQ → 回"这个博客账号已经跟别的 QQ 牵过手了……先在网页那边解绑，再回来找我吧。"
4. 成功 → 写入 `qq_uin`，回"记住你啦，以后随时都可以来找我说话。群聊里记得 @ 我一声。"

失败不提示"第几条规则"，只给对应的一句人类可读文案；后端日志记录原因，但不写绑定码明文。

### 4.4 解绑

只能在网页端操作：

- 清空 `qq_uin`；
- 让绑定码失效并立即生成新码（新码同步给后端）；
- 解绑后，这个 QQ 再发消息就回到"未绑定"状态；
- 网页解绑需要确认弹窗：`confirm('解绑后这个 QQ 将无法再和我聊天，确定吗？')`。

### 4.5 命令系统（要为后续命令留好接口）

命令不是"一个 if 判断"，而是一个**注册表**，以后加命令只往表里加一项，不动消息处理流程：

```python
@dataclass(frozen=True)
class Command:
    name: str                  # 规范名，小写，例如 "绑定"
    aliases: tuple[str, ...]   # 别名，例如 ("bind",)
    scope: str                 # "private" = 只在私聊执行；"any" = 私聊和群聊都行
    help: str                  # 一行说明，/帮助 直接用
    handler: Callable[[CommandContext], str]   # 返回要发送的文本

COMMANDS: dict[str, Command] = {
    "绑定": Command("绑定", ("bind",), "private", "把 QQ 绑定到博客账号：/绑定 1234-5678", cmd_bind),
    "帮助": Command("帮助", ("help", "commands"), "any", "看看我会哪些命令", cmd_help),
}

def dispatch(ctx: CommandContext) -> str | None:
    """命中返回回复文本，未命中返回 None。永远不调用 agent。"""
```

- `CommandContext` 带上：`qq_uin`、私聊/群聊、`group_id`、原始参数、是否已绑定、`is_admin`。
- 查找时先规范化命令词（去空格、转小写、全角转半角），再按 `name`/`aliases` 匹配。
- **`scope="private"` 的命令在群里调用**：统一回"私聊我一下"（`/绑定` 就是这一类，避免绑定码在群里经手）。
- 未注册的命令：回"这条咒文我没见过呢……我目前会的是：<列出所有 help>"，同样不交给梅林。
- `/帮助`（别名 `/help`、`/commands`）由注册表自动生成文案，新增命令不用再改它。
- 命令的处理顺序在"去重 → @ 触发判断"之后、"未绑定拦截 → 额度 → agent"之前：命令自己对自己的权限负责，不会消耗额度。

QQ 侧**不提供**解绑命令，避免拿到手机的人顺手解绑。

## 5. QQ 消息行为

### 5.1 私聊

- **未绑定（且不在 `QQ_ADMIN_USERS` 里）**：不回 AI，只回固定引导文案，用梅林的口吻说完整流程：

  > 诶，我还不太认识你呢。想和我聊天的话，先回博客一趟——登录之后打开「个人资料」，那里有张写着「Live2D 小助手 · QQ 绑定」的小卡片，里面会有一串绑定码。拿到以后回来跟我说一句「/绑定 1234-5678」，我就记住你啦。

  **每收到一条消息就回一次**，不做时间窗节流（站长明确要求）。
- **已绑定**：正常走 agent，历史按 QQ 号独立保存（私聊与群聊的历史分开）。
- **私聊里发 `绑定 ...`**：已绑定的 QQ 回一句"我早就记住你啦。要是想换绑，得先回博客那边解绑一下哦。"

### 5.2 群聊

- 白名单群 + @ 梅林的现有逻辑不变。
- 已绑定的用户：正常回复，额度按 §6 计算。
- 未绑定的用户：**只引导去私聊**，不在群里展开流程、不贴绑定码：

  > 这位朋友，我们好像还没正式认识呢。悄悄来私聊我一下，我告诉你怎么打招呼。

  **每次 @ 都回一次**，不做时间窗节流。
- 群里**不显示**任何绑定码或绑定状态。

### 5.3 管理员

- 绑定的账号是 WordPress 管理员 → 不限量，且**不计入** QQ 全站总额（和网页一致）。
- 未绑定、但 QQ 号在 `QQ_ADMIN_USERS` 白名单里的（站长自己的小号）→ 仍然不限量，保证机器人坏了也能自救。
- 其余一律按 §6。

**后端怎么知道"绑定账号是管理员"**：QQ 事件里没有 JWT，而 `user_profile` 只有 `tier`（`user`/`member`）。所以插件在推送绑定码时**一并推送 `is_admin`**，存进 `user_profile.is_admin`；每次打开个人资料页都会重推一次，角色变化最迟在用户下次打开资料页时生效。`is_admin` 只决定"是否豁免额度"，不授予任何管理能力（QQ 侧本来就没有管理入口），所以即使短暂滞后也不构成越权。

### 5.4 QQ 不可用时的行为

- 后端/agent 异常：回"抱歉，我这边好像出了点岔子，稍后再来找我一次吧。"
- 额度用尽：回"今天的魔力用完了，明天再来找我吧。"
- 全站 QQ 额度用尽：回"今天大家聊得太热闹，我的魔力见底了，明天再来吧。"
- 绑定码无效：回"这串咒文对不上呢……回博客的个人资料页看看最新的绑定码吧。"
- 绑定成功：回"记住你啦，以后随时都可以来找我说话。"

### 5.5 固定文案的两条硬规则

1. **一律梅林口吻**：第一人称、活泼但不谄媚，可以带一点魔法师的自称（"魔力""咒文"），但**操作信息不能丢**——去哪（个人资料页）、拿什么（绑定码）、发什么格式（`/绑定 1234-5678`）三要素必须完整。禁止出现"系统""接口""绑定状态""用户 ID"这类工程词。
2. **只在收到消息后回复，绝不主动推送**：没有定时任务、没有上线提醒、没有"你还没绑定"的催促。未绑定的用户不发消息，就一条消息都不会收到。

## 6. 额度

### 6.1 开关

WordPress 后台新增一个开关：**QQ 与网页共享额度**（`qq_quota_shared`）。默认**关闭**——先让 QQ 和网页各自独立跑，站长确认没问题后再合并。

### 6.2 共享模式（开关打开）

QQ 消息授权给绑定的 WordPress 用户，直接复用现有 `QuotaStore.reserve(user_id, limit, global_limit=...)`：

- `limit` 按绑定账号的 tier 取：会员用 `member_daily_quota`，普通用户用 `daily_quota`；
- 消耗顺序与网页完全一致：每日 → 额外额度 → 全站硬上限；
- 每日用量、全站用量与网页**同一个计数器**，所以网页额度条会立刻反映 QQ 的消耗；
- **同时**仍然占一个 QQ 专用的全站计数（见下），失败则两边的计数一起回滚。

### 6.3 独立模式（开关关闭，默认）

一套并行的 QQ 额度，与网页互不影响：

| 设置项 | 默认 | 说明 |
| --- | --- | --- |
| `qq_daily_quota` | 10 | 每个 QQ 每天条数（0 = 不能聊） |
| `qq_member_daily_quota` | 30 | 绑定账号是会员时每天条数 |
| `qq_global_daily_quota` | 0 | QQ 全站每天合计（0 = 不限） |
| `qq_unlimited` | 关 | 全站不限量开关 |

- 会员判定复用 `tier_of(bound_user_id)`（到期自动降级）。
- `qq_unlimited` 打开时：忽略按人和按会员两档，所有人（非管理员）想聊多少聊多少。它**只在独立模式下有意义**；共享模式下"按人额度"就是网页额度，不受这个开关影响。
- **`qq_global_daily_quota` 在两种模式下都生效**（包括共享模式和不限量模式）：它是 QQ 一侧自己的兜底阀，用**独立的 QQ 全站计数器**，不读网页的全站计数。也就是说共享模式下一条 QQ 消息会同时占用"网页全站计数"和"QQ 全站计数"两个桶——前者是网页的总额度，后者是站长单独给 QQ 留的闸门。这样哪怕网页额度还很宽裕，站长也能用 `qq_global_daily_quota` 单独卡住 QQ。
- 独立模式**不消费额外额度**。
- 计数表：`qq_daily_usage(qq_uin, day, used)`、`qq_global_usage(day, used)`；按 `QUOTA_TIMEZONE` 跨零点重置。
- 占用顺序：先按人（或跳过），最后占全站；全站失败则整个事务回滚（与 `QuotaStore.reserve` 相同的语义）。

### 6.4 管理员豁免

管理员（绑定账号是 WP 管理员，或在 `QQ_ADMIN_USERS` 里）不占任何 QQ 计数，直接放行。

### 6.5 退款

QQ 消息**没有产出任何正文**时退回额度：agent 抛异常、超时、只拿到 error 事件——这些都算没产出，回给用户的"我这边有点问题"不算一次消耗。判据是"是否产生过 delta 文本"，和网页 `chat.py` 里的退费规则一致；共享模式退的是 `QuotaStore` 那一份（连带 QQ 全站计数），独立模式退的是 QQ 计数。

## 7. 设置项与后台 UI

**QQ 的独立额度参数一律在 WordPress 后台设置**（和现有的普通用户额度、全站总额放在同一个页面），站长不需要改 `.env`、也不需要重启后端：

WordPress 设置页（"Live2D 小助手 · 聊天额度与运行参数"）新增一段 **QQ 通道**：

- QQ 与网页共享额度（开关）
- QQ 每人每日额度（数字，0–1000）
- QQ 会员每日额度（数字，0–1000）
- QQ 全站每日额度（数字，0–1000000，0 = 不限）
- QQ 不限量（开关，开启时提示"按人和按会员额度将不生效，全站额度仍然生效"）

这些值通过现有 `PUT /api/admin/settings` 写进 `runtime_settings.json`，存下来立即生效（和 `daily_quota` 一样，不需要重启）。`.env` 里对应的环境变量只作为**初始默认值**（`QQ_DAILY_QUOTA=10`、`QQ_MEMBER_DAILY_QUOTA=30`、`QQ_GLOBAL_DAILY_QUOTA=0`、`QQ_QUOTA_SHARED=false`、`QQ_UNLIMITED=false`）。

后端 `RuntimeSettingsUpdate` 需要支持布尔字段（目前只有 int/str），并加进 `_INT_RANGES` / `_BOOL_FIELDS`；`GET /api/admin/settings` 自动带出。

WordPress 后台"用户与额度"页：`qq_uin` 列开始显示真实值（已有列，不用改表头）；最好在列里附带"已绑定/未绑定"的语义（`—` 仍表示未绑定）。

## 8. 数据与接口

### 8.1 数据模型（`backend/app/credits.py` 的 schema 常量）

- `user_profile` 增加 `bind_code_hash TEXT` 与 `is_admin INTEGER NOT NULL DEFAULT 0`（启动时用 `PRAGMA table_info` 判断后 `ALTER TABLE ADD COLUMN`，兼容已有数据库）。
- 唯一约束：`CREATE UNIQUE INDEX IF NOT EXISTS ... ON user_profile(qq_uin) WHERE qq_uin IS NOT NULL`（SQLite 支持部分索引；现有行全是 NULL，可以直接建）。
- 新表：`qq_daily_usage`、`qq_global_usage`。

### 8.2 接口

| 方法 | 路径 | 鉴权 | 用途 |
| --- | --- | --- | --- |
| `GET` | `/api/me/bind` | 用户 JWT | 返回 `{qq_uin: str \| null}` |
| `PUT` | `/api/me/bind-code` | 用户 JWT | `{code, is_admin}`，后端存哈希与管理员标记；返回 204 |
| `DELETE` | `/api/me/bind` | 用户 JWT | 解绑当前账号的 QQ；返回 204 |
| `DELETE` | `/api/admin/users/{user_id}/bind` | 管理员 JWT | 强制解绑（删除用户时用）；返回 204 |

QQ 侧的绑定命令不走 HTTP 对外接口，直接在 `QQAdapter` 内处理（它已经能拿到 QQ 号）。

WordPress → 后端的用户身份调用：插件用现有签名密钥为**当前登录用户**签发一个短时用户 JWT（`admin=false`），不需要新密钥。

### 8.3 与现有边界的关系

- 邮箱仍然只存在 WordPress；本次新增的绑定状态是**运行状态**，不是身份信息，所以放在后端额度库合理。
- 绑定码明文只存在 WordPress，后端拿不到原码。

### 8.4 账号被删除

WordPress 删除用户时触发 `deleted_user` 钩子，插件用管理员令牌调用 `DELETE /api/admin/users/{user_id}/bind`，把 `qq_uin` 清空。否则那个 QQ 会永远显示"已经绑定过了"，而账号已经登不进去——只能手动改库。

## 9. 安全

- 绑定码是"把某个 QQ 挂到我的账号"的凭证：只在本人登录后的资料页可见；后端只存哈希；刷新即失效；解绑即换码。
- 防覆盖：绑定动作必须在**两个条件下**同时成立——持有绑定码 + 控制该 QQ。已经绑定过的 QQ 必须先网页解绑，才能被重新绑定。
- 群聊里不暴露绑定码、账号 ID、邮箱。
- 日志只记 `qq_uin` 与结果，不写绑定码。
- 引导文案与错误回复**不做时间窗节流**：收到一条需要回复的消息就回一条。绑定码是 8 位数字（10^8 空间）、可随时刷新，QQ 平台自身也有消息频率限制，穷举不现实，所以不额外加"尝试次数"限制，避免用户被莫名其妙地静音。

## 10. 验收

1. 未绑定私聊 → 看到引导；发送错误绑定码 → 明确提示无效。
2. 正确绑定码 → 绑定成功；同一 QQ 再次发送 → 提示已绑定。
3. 换一个账号用同一个 QQ 绑 → 被拒绝，提示先解绑。
4. 网页解绑后旧码失效；刷新出新码后可用新码重新绑定。
5. 开关开启：QQ 聊一条，网页额度条同步减少（含额外额度被消耗的情形）。
6. 开关关闭：QQ 消耗不改动网页额度；QQ 每人额度用尽后拒绝。
7. QQ 全站额度设为 2：前两条成功，第三条被拒；共享与独立两种模式各验证一次（共享模式下同时验证网页全站计数也在涨）。
8. 打开 QQ 不限量：按人额度不再生效，但 QQ 全站额度仍然拦截。
9. 管理员绑定后不限量，且不占用 QQ 全站计数。
10. `wp-admin/profile.php` 卡片在普通用户、会员、管理员三种账号下显示正确；后端不可达时降级为提示。
11. 以上 QQ 额度参数全部在 WordPress 后台修改后立即生效，不需要改 `.env`、不需要重启。
12. Agent 出错（没有任何正文产出）时额度退回，用户第二天仍能正常聊天。
13. 删除一个已绑定的 WordPress 用户后，那个 QQ 恢复"未绑定"，可以重新绑定到新账号。
14. 未绑定的 QQ 每次私聊、每次在群里 @ 都会收到一次提示，不因时间间隔被静音。
15. 未绑定的 QQ 不发消息时，**不会收到任何主动消息**（没有定时提醒、没有上线通知）。
16. 所有固定文案读起来像梅林在说话，不是系统通知；同时都包含"个人资料页 / 绑定码 / /绑定 1234-5678"这类可操作信息。
17. 以 `/` 或 `\` 开头的消息一律当命令：`/今天天气怎么样` 只回"没这条命令"，不会得到 AI 回答，也不会进对话历史；`/绑定` 参数格式不对时回格式提示而不是静默。
18. `/帮助` 自动列出注册表里的所有命令（含 `绑定`）；新增一条命令时只需要在 `COMMANDS` 里加一项，`/帮助` 和未知命令提示都会自动带上它。

## 11. 风险与回滚

- **误绑**：只能通过本人登录 + 绑定码，风险低于"填 QQ 号即绑"的方案；解绑按钮始终可见。
- **绑定码泄露**：持有码的人可以把自己的 QQ 绑到泄露者的账号上，消耗其额度；受害者可在网页一键解绑并刷新码。若账号已绑定，泄露的旧码无效。
- **回滚**：新表和新列都是增量；把 WordPress 后台开关恢复默认（共享关闭）即可让 QQ 回到独立额度；`qq_uin` 可以批量清空回退到"全部未绑定"。不需要回滚数据库。

## 12. 留给实现者的决定

- QQ 历史缓存的键怎么区分私聊与群聊（建议 `("private", qq_uin)` / `(group_id, qq_uin)`，保持现有内存结构）。
- QQ 独立额度的具体 SQL 形态，是否复用 `QuotaStore` 事务风格（建议独立 `QQQuotaStore`，但沿用"每日→全站"的两段式）。
- 命令分发器放在哪一层（建议在 `QQAdapter` 内、`_reply()` 之前，命令表用一个 dict：`{"绑定": ..., "bind": ...}`，未知命令走统一兜底），以及以后要不要加 `/帮助`。
- 引导文案的措辞，只要包含"个人资料页""绑定码""/绑定 1234-5678"三个要素即可。
